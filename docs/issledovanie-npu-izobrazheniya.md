# Исследование генерации изображений на Hexagon NPU

Это исследование, а не готовый генератор. Работоспособность на SM8635 ещё не подтверждена.

В качестве основы рассмотрен [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) (ревизия 008b9a2): он поддерживает SD 1.5, GGUF/Q4_0, выбор backend и ускоренные методы сэмплирования. Для 4–8 шагов требуется подходящая дистиллированная модель или LCM/совместимая LoRA: обычная Anything V3 не становится LCM только из-за уменьшения числа шагов. Сам проект не добавляет обязательный фильтр безопасности.

Локально статическая библиотека stable-diffusion.cpp собрана под Linux x86-64 с исходниками ggml llama.cpp b12211. Это проверяет компиляцию, **но не** Android ABI, совместимость с поставляемыми бинарными .so или выполнение на устройстве.

Критическая преграда для требования «только NPU»: в `src/core/compute_workspace.cpp` stable-diffusion.cpp добавляет CPU backend в scheduler даже при выборе HTP0. Наличие операций CONV и IM2COL в Hexagon не доказывает поддержку всех конкретных форм тензоров SD 1.5. До интеграции нужно проверять распределение всех вычислительных узлов графа, явно отказывать при CPU/GPU fallback и протестировать текстовый энкодер, UNet и VAE на устройстве. Некоторые операции подготовки данных могут выполняться на хосте; для вычислений модели fallback запрещён.

Дополнительно необходимо проверить ограничение памяти FastRPC на конкретном устройстве, освобождать языковую модель перед загрузкой диффузионной и обратно, и тестировать реальные Q4_0-веса, размеры тензоров и качество. На SM8635 следует отдельно проверить режим HVX без HMX. Расчёт размера модели по одной лишь степени квантования не гарантирует, что она поместится вместе с VAE, текстовым энкодером и активациями.

Foreground service повышает приоритет процесса, но не гарантирует сохранение в ОЗУ: Android может завершить процесс при нехватке памяти, пользователь может остановить сервис, а устройства применяют собственные ограничения. Разрешение уведомлений Android 13+ нужно запрашивать, но оно не является гарантией неубиваемости процесса.

## Альтернатива: Qualcomm QNN / QAIRT

[Qualcomm AI Hub: Stable Diffusion v1.5](https://huggingface.co/qualcomm/Stable-Diffusion-v1.5) публикует варианты text encoder, UNet и VAE для QNN в W8A16. [Документация Qualcomm](https://workbench.aihub.qualcomm.com/docs/hub/compile_examples.html) описывает QNN context binary как привязанный к устройству формат для NPU. Это перспективный путь без неявного CPU fallback для вычислений моделей; не следует подменять отсутствие подходящего NPU-контекста CPU/GPU реализацией. Токенизация, подготовка данных и сам алгоритм сэмплирования вне графов могут оставаться на CPU — это нужно оговорить отдельно от инференса нейросетей.

Готовый пакет для Snapdragon **8 Gen 3** не является доказательством совместимости с **8s Gen 3 (SM8635)**: нужны подходящие бинарные контексты, runtime и испытание на конкретном устройстве. В опубликованных выше примерах основной точности указан W8A16, а не Q4. Поддержку Q4 для полного конвейера, конвертацию Anything V3 и возможность 4–8 шагов надо проверить отдельно. Для LCM потребуется совместимая модель/LoRA, вкомпилированная в контекст; обычный FP16 checkpoint напрямую QNN не исполняет.

[Local Dream](https://github.com/xororz/local-dream) заявляет поддержку SD 1.5 на Hexagon v68 и новее и использует QNN. Однако на проверенной ревизии [его SD 1.5 text encoder выполняется через MNN на CPU](https://github.com/xororz/local-dream/blob/2f1f3ba186eeca2a52268540108b3ee6e2296d17/app/src/main/cpp/src/main.cpp#L53), поэтому переносить его конвейер как NPU-only нельзя. Лицензия репозитория — CC BY-NC 4.0; использование кода также требует отдельной проверки совместимости лицензий. Другой путь — скомпилировать все три графа через Qualcomm AI Hub / QAIRT и связать их с Android-приложением с явной проверкой HTP backend, версий SDK и лицензий.

## План оставшейся работы

* API и foreground service должны владеть общей с чатом сессией модели: завершение Activity не должно освобождать модель при активном сервисе. Нужна сериализация загрузки, генерации и выгрузки.
* API по умолчанию должен слушать только loopback, иметь ограничение запросов и не сохранять историю. Открывать доступ в сеть без защиты нельзя.
* Сервис должен показывать состояние и действия в уведомлении; запрос POST_NOTIFICATIONS на Android 13+ не заменяет сам foreground service. Для target SDK 36 требуется корректный тип foreground service и соответствующие разрешения.
* Генератор нельзя объявлять готовым до проверки всех трёх сетей на HTP и их запуска с подходящими моделями на SM8635; при неподдерживаемом графе — понятная ошибка вместо CPU/GPU fallback.

## Уточнение по Android-интеграции (QNN через ONNX Runtime)

Существует опубликованный Android AAR `com.microsoft.onnxruntime:onnxruntime-android-qnn` с QNN Execution Provider и зависимостью от Qualcomm QNN runtime. Например, по [POM 1.27.0](https://central.sonatype.com/artifact/com.microsoft.onnxruntime/onnxruntime-android-qnn/1.27.0) его зависимость — QNN runtime 2.42.0. Сочетание версий следует проверять для конкретных бинарных контекстов: нельзя считать, что контекст, скомпилированный с другой версией QAIRT или для другой модели SoC, автоматически загрузится.

В ONNX Runtime есть [настройка `session.disable_cpu_ep_fallback=1`](https://github.com/microsoft/onnxruntime/blob/v1.22.0/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h): если провайдер не поддерживает все узлы, создание сессии должно завершиться ошибкой. Её нужно установить отдельно для каждого графа text encoder, UNet и VAE, выбрать именно QNN HTP backend, не добавлять CPU EP явно и проверять фактический backend на устройстве. Это предотвращает тихий CPU fallback в графе, но само по себе не доказывает успешную работу на SM8635.

[Шаблоны Qualcomm](https://github.com/quic/ai-hub-models/blob/main/src/qai_hub_models/models/templates/diffusion/stable_diffusion.py) имеют другие имена и формы входов, чем многие стандартные ONNX-экспорты: например, `tokens` у text encoder и `latent`, `timestep`, `text_emb` у UNet. Поэтому универсальный SD-клиент нельзя просто подключить к этим файлам без адаптации и проверки сигнатур. Потребуются также CLIP-токенизатор, согласованный scheduler и типы/масштабы выходных тензоров. Сырые `.safetensors`/GGUF не являются готовыми QNN context binaries.

Для проверки на реальном аппарате необходим набор совместимых графов именно для SM8635 с известными версиями QNN, формами входов и токенизатором. На текущий момент ни такого проверенного набора, ни готового Android-пайплайна генерации в репозитории нет; публикация APK с заявленным работающим генератором была бы преждевременной.

## Кандидат: аниме SD 1.5 за 4–8 шагов и QNN Plugin EP

[onnxruntime/onnxruntime-qnn](https://github.com/onnxruntime/onnxruntime-qnn) — именно QNN Execution Provider для ONNX Runtime, а не готовый генератор или файл модели. Поддерживается Android ARM64 через Maven; современный плагин 2.x регистрируется отдельно. По [документации плагина](https://github.com/onnxruntime/onnxruntime-qnn/blob/main/docs/execution_providers/QNN-ExecutionProvider.md) версия 2.8.0 проверена с ORT Android 1.29.0 и QNN runtime 2.52.0. Требуется отдельно указать HTP backend и запретить CPU fallback; простая установка плагина не гарантирует NPU-only выполнение.

Для первого кандидата подходит [Disty0/LCM_SoteMix](https://huggingface.co/Disty0/LCM_SoteMix): модель описана автором как аниме SD 1.5 с LCM, рекомендуются 4–8 шагов, LCM sampler и CFG 0 или 1. Это **кандидат**, не проверенный нами QNN-контекст для SM8635. Другой путь — объединить подходящий SD 1.5 anime checkpoint с совместимой [LCM-LoRA](https://github.com/huggingface/blog/blob/main/lcm_lora.md) до экспорта/квантования; качество и совместимость нужно проверять для каждой пары.

Предлагаемый экспериментальный конвейер: конвертировать выбранную модель в три совместимых QNN/ONNX графа CLIP, UNet и VAE, сохранять tokenizer и точные параметры LCM scheduler; подготовить/скомпилировать графы под SM8635, с закреплением версий ORT/QNN и проверкой входов/выходов. На устройстве выполнять нейросетевые графы исключительно на HTP, запрещая CPU fallback; токенизация, сэмплер и кодирование PNG выполняются как обычный вспомогательный код на CPU. Выгружать LLM до загрузки графов и освобождать графы перед загрузкой LLM. Сначала использовать известный для QNN W8A16, а Q4 считать отдельным исследованием и не обещать его поддержку до тестов.

[Local Dream](https://github.com/xororz/local-dream) заявляет поддержку SD 1.5 на Hexagon v68+, однако в его SD 1.5 пайплайне CLIP работает на CPU: это доказательство перспективности NPU для части графа, но не доказательство выполнения **всех** сетей на NPU в нашем приложении. Совместимость и стабильность на SM8635, качество 4–5 шагов и возможность одновременного размещения графов пока не подтверждены.

Включение весов в APK или отдельный пакет требует проверить лицензию конкретного checkpoint, его производных и распространяемых runtime-библиотек. Для первой экспериментальной версии удобнее отдельный загружаемый пакет с версиями, лицензиями и SHA-256: это позволит обновлять модели независимо от APK и не сохранять гигабайты в Git. Возможность распространения конкретного LCM_SoteMix пока не подтверждена.

### Реализованный подготовительный компонент

В проект добавлен `LcmScheduler`: расчёт расписания и денойзинга для SD 1.5/LCM с `epsilon`-предсказанием и scaled-linear beta schedule. Это не генератор и не вызов модели; компонент рассчитывает вспомогательные операции на CPU, как и предусмотрено выше. Тесты проверяют 4/5-шаговые расписания, числовые примеры и некорректные входы. Настройки scheduler должны совпадать с конкретным checkpoint — одной реализации scheduler недостаточно для запуска QNN.

## Готовый кандидат HTP v73 и допущение CPU для CLIP

Для нового направления пользователь допускает выполнение CLIP на CPU при условии, что UNet и VAE работают на NPU. Наиболее перспективный найденный готовый пакет — [latentdivergence/dreamshaper8-lcm-npu-8gen2](https://huggingface.co/latentdivergence/dreamshaper8-lcm-npu-8gen2), ревизия `6a2e524fe1e74f8050ea169f6cec1f725f956d90`: DreamShaper 8 с встроенной LCM-LoRA, 4 шага, CFG 1, W8A16. В пакете три ONNX EPContext-обёртки с QNN context binaries, `quant.txt`, `tokenizer/vocab.json` и `tokenizer/merges.txt`. По карточке модели входы UNet — `timestep`, `latent`, `text_emb`, тензоры uint16. Веса модели отдельно от APK, их лицензии необходимо соблюдать.

Snapdragon 8 Gen 2 и 8s Gen 3 имеют v73, но аппаратная архитектура не гарантирует совместимость QNN context binaries между разными SoC, версиями драйвера и QAIRT; реальная проверка на SM8635 обязательна. Данный пакет не Anything V3, поэтому это промежуточный вариант, а не подтверждённая аниме-модель Anything. Anything V3 дополнительно потребуется конвертировать/найти готовую QNN версию; её меньший размер относительно другой модели нельзя утверждать без сравнения конкретных файлов и формата.

В качестве другого варианта [Q-P1NG Q-Dream](https://huggingface.co/Q-P1NG/qdream-models) предоставляет DreamShaper 8 LCM v73 с CPU CLIP (MNN) и QNN UNet/TAESD (~1 ГБ). Это другой формат: бинарные QNN contexts напрямую, а не ONNX EPContext; бинарные файлы не взаимозаменяемы без адаптера. Требуется соблюсти отдельную лицензию пакета. Исходники Local Dream распространяются под CC BY-NC 4.0, в отличие от GPL этого приложения; копирование его кода без проверки совместимости лицензий не допускается.

Добавлен отдельно тестируемый `AffineUInt16Quantizer` для работы с аффинными scale/zero-point согласно `quant.txt`. Он не выполняет инференс; в генераторе необходимо проверять типы, раскладки и имена тензоров по самой модели, а не полагаться только на эти примеры.

### Подготовка QNN Runtime

В Gradle подключены ORT Android 1.29.0, QNN Plugin EP 2.7.0 и QNN Runtime 2.51.0. В `QnnHtpRuntime` добавлено создание сессии EPContext с явным HTP backend и `session.disable_cpu_ep_fallback=1`. Компонент экспериментальный, ещё не подключён к UI и не прошёл проверки на устройстве; его вызов возможен только после освобождения LLM и организации единого владения NPU. Его наличие не означает готового генератора. В частности, требуется подтвердить совместимость модельных контекстов с этой версией QNN и SM8635.

### Дополнительный блокер uint16 для выбранного пакета

Кандидат DreamShaper8 EPContext принимает uint16-тензоры. Проверка [исходников ORT Java 1.29.0](https://github.com/microsoft/onnxruntime/blob/v1.29.0/java/src/main/java/ai/onnxruntime/OnnxJavaType.java) показывает, что отдельного `OnnxJavaType.UINT16` нет: UINT16 отображается как подписанный носитель INT16. [Фабрика тензоров из ShortBuffer](https://github.com/microsoft/onnxruntime/blob/v1.29.0/java/src/main/java/ai/onnxruntime/OnnxTensor.java) создаёт именно INT16/FLOAT16/BFLOAT16, поэтому подавать данные этой модели как `INT16` нельзя — тип графа не совпадёт. Добавлен unit-тест этого ограничения.

В качестве экспериментального обхода добавлен адаптер к существующему внутреннему JNI ORT (описан ниже); он ещё не проверен на устройстве. Альтернатива — отдельный native C/C++ интерфейс ORT или другой комплект графов. Кроме этого нужны токенизация, соединение трёх графов с sampler, управление памятью NPU и UI. Один только `QnnHtpRuntime.open` не выполняет модель и не является генератором.

### Экспериментальная оркестрация LCM

`LcmImagePipeline` связывает интерфейсы текстового энкодера, UNet и VAE с LCM-сэмплером: batch 1, CFG 1, масштаб латента SD 1.5 0,18215 и настраиваемое преобразование выхода VAE в [0, 1]. Диапазон выхода должен соответствовать конкретному графу: нельзя без проверки считать, что каждый VAE выдаёт [-1, 1]. Тесты используют исключительно заглушки и проверяют порядок вызовов, шаги, масштаб, воспроизводимость и ошибки. Это **не готовый генератор**: адаптеры конкретных моделей, токенизатор, проверенная на устройстве передача UINT16, импорт комплекта модели и интерфейс отсутствуют. Код оркестрации сам по себе не проверяет NPU; реальный адаптер UNet/VAE должен обеспечивать HTP и проверку ошибок, а не молча выполнять модель на CPU. Результаты на SM8635 пока неизвестны.

### Экспериментальный UINT16 для ORT 1.29

`ai.onnxruntime.UInt16TensorFactory` использует внутренний JNI-метод ORT Java 1.29 через reflection с типом UINT16 и удерживает прямой буфер до закрытия тензора. Это временный адаптер к непубличному API, не универсальное решение: при обновлении ORT нужно перепроверить сигнатуру и JNI-преобразование типа. Для R8 добавлено правило сохранения метода. Android instrumentation-тест проверяет тип, побитовое содержимое и ошибки размеров; его ещё необходимо запустить на устройстве, включая release-сборку. Адаптер пока не подключён к графам, а тест не доказывает выполнение на HTP.

### Обобщённый адаптер QNN UINT16

`QnnUInt16Graph` проверяет имена, фиксированные формы и типы входов/выхода графа по явно переданной конфигурации, квантитизирует входы, запускает строгую HTP-сессию и деквантитизирует выход. Параметры необходимо получить из проверенного комплекта модели; сам класс не определяет их автоматически и пока не связан с UNet, VAE и UI. Работа с действительным контекстом и совместимость с устройством не проверены.

### Экспериментальный CLIP BPE

`ClipBpeTokenizer` принимает словарь и упорядоченные слияния извне и формирует 77 токенов SD 1.5, включая BOS/EOS и усечение. Тесты включают искусственный мини-словарь и несколько векторов OpenAI CLIP для английского и кириллицы. Очистка ввода здесь не повторяет `ftfy` и HTML-unescape эталонного CLIP, поэтому результаты для отдельных строк могут отличаться; сверка с настоящим токенизатором выбранного пакета ещё необходима. Загрузка `vocab.json` и `merges.txt` реализована, но Android-тест чтения ещё нужно запустить на устройстве. Подключение CLIP-графа пока не реализовано.

В ONNX-обёртке кандидата UNet присутствуют узлы QuantizeLinear/DequantizeLinear вокруг EPContext. Доступная строгая настройка запрета CPU fallback может не позволить загрузить такой граф; распределение операторов должно проверяться на устройстве, а не предполагаться по наличию EPContext.

### Проверенные сигнатуры DreamShaper 8gen2

CI `42666387460` скачал только три ONNX-обёртки закреплённой ревизии и проверил их SHA-256. CLIP: `tokens` INT32 `[1,77]` → `text_embedding` UINT16 `[1,77,768]`. UNet: `timestep` UINT16 `[1,1]`, `latent` UINT16 `[1,64,64,4]`, `text_emb` UINT16 `[1,77,768]` → `output_latent` UINT16 `[1,64,64,4]`. VAE: `latent` UINT16 `[1,64,64,4]` → `image` UINT16 `[1,512,512,3]` (NHWC). Масштабы и zero points также прочитаны из самих графов и совпадают с `quant.txt`; добавлен экспериментальный `DreamShaperLcm`, который их использует. Он пока не подключён к интерфейсу и не проверен на устройстве.

Выявлено ограничение качества: scale временной метки UNet равен 0,0122224763, zero point 0, поэтому UINT16 представляет значение лишь до ~801; стандартное расписание LCM начинается с 999, которое при квантовании насыщается. На данном этапе это известный непроверенный компромисс, а не подтверждение корректного качества модели. Требуется проверить с автором комплекта или на устройстве. Дополнительно Q/DQ вокруг EPContext могут быть несовместимы со строгим запретом CPU fallback.
